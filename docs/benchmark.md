# Benchmark: native 64-bit API vs native 32-bit API vs the 16-bit DOS VM

UEFI-DOS runs programs three ways. This page measures what each way costs, with
the same eight workloads, the same byte counts and the same checksums in all
three, so the numbers can be compared directly.

| world | what runs | how it is timed |
| --- | --- | --- |
| **16-bit DOS VM** | `BENCH16.COM`, interpreted by the internal 8086 core, calling INT 21h for DOS services | `INT 1Ah AH=00h` — the 18.2 Hz BIOS tick counter (54.925 ms) |
| **native 64-bit** | `BENCH64.EXE` (PE32+), loaded by `RUN64`, calling the SDK's `struct uefidos_exports` | `RDTSC` |
| **native 32-bit** | `BENCH32.EXE` (PE32), same source, same API, loaded by `RUN64` from the IA32 build | `RDTSC` |

Everything lives in [`bench/`](../bench): `make_bench16.py` generates the 16-bit
program **and** `bench/bench_sizes.h` (the C halves include it, so the two sides
cannot drift apart), `bench.c` is the native program for both widths,
`build_bench.ps1` builds all three plus the benchmark image, and
`run_bench.ps1` runs the host phase and the UEFI phase and writes
[`bench/results.md`](../bench/results.md).

## Workloads

| workload | work per pass | checksum | what it stresses |
| --- | --- | ---: | --- |
| `alu` | 2,621,440 iterations of `x = x*1103 + 12345` (16-bit LCG, x in a register) | `0001` | interpreter dispatch, register/flag handling |
| `fill` | 192 × 32,768 bytes written with `STOSB` | `00FF` | byte stores, memory bandwidth |
| `copy` | 144 × 16,384-byte byte copies (`MOV`/`INC`/`LOOP`, not `REP`) | `00FF` | load/store throughput |
| `scan` | 96 × 32,768 bytes summed into a 32-bit accumulator | `17E8` | loads + 32-bit arithmetic in 16-bit code |
| `api` | 524,256 × `INT 21h AH=30h` vs `svc->get_version()` | `FF80` | DOS-call overhead |
| `text` | 3,145,536 × one console character (`AH=02h` vs `rt_putc`) | `FF40` | BIOS/DOS character output path |
| `file` | create, write 132,096 bytes in 1,024-byte blocks, close, reopen, read back, close, delete | `0400` | DOS file I/O over the FAT driver |
| `find` | 10 full `\BDATA\*.*` scans of a 120-file directory (`AH=1Ah/4Eh/4Fh`) | `04B0` | directory enumeration |

The checksum column is a real assertion: a world that does not do exactly the
same work cannot print the same value. Each workload is reported as one line,

```
BENCH alu tick=20 cs=0001        (16-bit: 55 ms ticks)
BENCH alu cycles=6025353 cs=0001 (native: TSC cycles)
```

## Results — same machine, real CPU (host harness)

Median of 3 runs on an i9-14900HX, TSC 2.4192 GHz, `-O2`, host harness build
(DOS VM and native 64-bit run on the same CPU, so the ratio is meaningful).

| workload | unit | 16-bit DOS VM | native 64-bit | 64-bit vs DOS |
| --- | --- | ---: | ---: | ---: |
| alu | ns/step | 1,424.8 | 4.0 | **358×** |
| fill | MB/s | 7.6 | 5,153.5 | **675×** |
| copy | MB/s | 3.9 | 4,653.6 | **1,192×** |
| scan | MB/s | 3.4 | 3,743.3 | **1,111×** |
| api | ns/call | 2,095.4 | 1.1 | **1,837×** |
| text | ns/char | 209.5 | 21.2 | **9.9×** |
| file | MB/s | below one tick | 110.3 | — |
| find | ns/entry | below one tick | 4,803.3 | — |

`file` and `find` finish in under 10 ms in the host DOS world (the image is a
memory-cached file), which is below the DOS clock's resolution; their honest
numbers come from the UEFI phase below.

## Results — under QEMU + OVMF with WHPX (guest executes on the real CPU)

The IA32 build cannot run PE32+ images and the x86_64 build cannot run PE32 ones,
so the 32-bit native world is measured with the IA32 image. Both worlds in this
table run inside the same virtual machine, which is what makes the ratio fair.

| workload | 16-bit DOS VM | native 32-bit | 32-bit vs DOS |
| --- | ---: | ---: | ---: |
| alu | 549,254 µs | 3,078 µs | **178×** |
| fill | 549,254 µs | 738 µs | **745×** |
| copy | 302,090 µs | 520 µs | **581×** |
| scan | 659,105 µs | 618 µs | **1,066×** |
| api | 82,388 µs | 415 µs | **199×** |
| text | 77.8 s | 77.6 s | **1.0×** |
| file | 29.2 s | 25.3 s | **1.2×** |
| find | 67.9 s | 66.3 s | **1.0×** |

The x86_64 image was measured the same way; `bench/results.md` keeps all four
columns (`16-bit DOS VM (host)`, `native 64-bit (host)`, `16-bit DOS VM (UEFI)`,
`native 32-bit (UEFI)`) as generated by the driver.

## What the numbers say

1. **CPU and memory-bound 16-bit code runs 180× to 1,200× slower than native.**
   That is the price of interpreting every instruction: the guest averages
   roughly 2M interpreted instructions/s, while native code does 3–5 GB/s of
   byte traffic on the same core. `copy` and `scan` are the worst cases because
   every guest byte costs several interpreted instructions.
2. **A DOS API call costs about 2 µs in the host harness and 0.16 µs in the
   UEFI build**, against about 1 ns for the same call in native code — a
   200×–1,800× gap. The difference between the two DOS numbers is the host
   build's own diagnostic overhead (`-DUEFIDOS_HOST` keeps tracing hooks that
   the release build compiles out), which is why the ratio must never be taken
   across environments.
3. **32-bit native and 64-bit native are within 1.3× of each other** on every
   CPU workload (`alu` 3.1 ms vs 2.6 ms, `scan` 618 µs vs 840 µs). The API gives
   the same speed at both widths; there is no penalty for 32-bit images and no
   windfall from 64-bit ones at this size.
4. **I/O-bound programs are already at native speed.** Console output
   (3.1M characters) and directory scans and file writes cost the same in both
   worlds under UEFI, because the time is spent in the platform — the serial
   mirror for `text`, the EFI block-I/O path for `file`/`find` — not in the
   guest. A DOS program that waits on the disk is not paying for the
   interpreter.
5. **The interpreter is the floor, the platform is the ceiling.** Adding
   native speed to a DOS program helps exactly to the degree that program is
   CPU-bound; a program dominated by screen output or disk access gains almost
   nothing until the platform path itself gets faster.

## Caveats

* The BIOS tick counter has 54.925 ms granularity. Every workload except
  `file`/`find` takes at least five ticks in the slowest world, so its error is
  ≤10%; `file` and `find` are only reported where they are measurable. `text`
  was tripled from 1M to 3.1M characters for that reason.
* `text` under UEFI is bound by serial mirroring, not by the guest: the console
  is copied to the serial port, so both worlds spend ~25 µs per character.
  Without the mirror (a real machine with a monitor) both are much faster and
  the guest side dominates again.
* `file` and `find` under UEFI are bound by firmware block I/O (about 55 ms per
  512-byte sector in this OVMF build). That is a property of the platform, not
  of the DOS VM or the native API.
* WHPX runs the guest on the real CPU, which is what "native" has to mean. With
  `-Accel tcg` the native images would run inside QEMU's own interpreter and the
  numbers would be garbage — the driver refuses to mix them (`-Accel whpx` is
  the default on Windows, `-Accel tcg` is accepted for machines without it and
  is reported in `results.md`).
* The 16-bit numbers include the emulator's host-side overhead (interrupt
  delivery, timing, the platform layer); a real 4.77 MHz 8088 would be far
  slower still. The comparison is "this emulator's DOS VM vs this machine's
  native execution", which is the question a user asks when deciding whether to
  rebuild a DOS program as native.

## Reproducing it

```
powershell -NoProfile -ExecutionPolicy Bypass -File bench/build_bench.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File bench/run_bench.ps1
```

Useful switches: `-Runs 5` (more repetitions, medians reported), `-SkipUefi`
(host harness only), `-ReuseHostLogs` (keep the host logs, re-run only the UEFI
phase), `-Accel tcg`, `-UefiTimeout 1200` (seconds per UEFI phase; the DOS phase
needs ~4 minutes because of `text` and `find`), `-OutFile bench/results.md`.

The driver needs `build\hosttest.exe`, `build\BOOTX64.EFI` and
`build\BOOTIA32.EFI` (it runs `build.ps1` if the EFI binaries are missing).

## Reading a run by hand

```
build\hosttest.exe --shell build\BENCH.IMG "BENCH16" "RUN64 BENCH64.EXE"
```

Under QEMU the same two commands come from `AUTOEXEC.BAT`
(`BENCH16` / `RUN64 BENCHxx.EXE` / `ECHO BENCH-DONE`); the driver watches the
serial log for `BENCH-DONE`. `UEFIDOS_HARD_STEPS` must be raised on the host
(default is small) or the native half will be cut off.
